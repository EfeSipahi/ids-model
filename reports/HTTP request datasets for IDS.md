# Outgrow CSIC 2010 Without Learning Dataset Shortcuts

Only five public datasets store whole, labeled HTTP requests that this project's extractor can read: CSIC 2010, ECML/PKDD 2007, SR-BH 2020, the open-appsec WAF Comparison Project and ATRDF. Three of them should carry the next phase. They are the **full CSIC 2010 corpus** (97,065 requests, only about 35,000 distinct), **SR-BH 2020** (907,814 real requests to one WordPress site, CC0 on Harvard Dataverse) and **open-appsec's 1,040,242 legitimate browser requests** (Apache-2.0) as modern benign traffic. ECML/PKDD, ATRDF, the 2026 ModSec-WP set and the 30-day ModSecurity logs belong in secondary or cross-dataset roles; the ModSecurity logs are the same public data already in `data/raw/owasp/`. Query-only sets, flow-only datasets, CIC PCAPs and most Hugging Face/Kaggle uploads should stay out of training. None of the good sets is clean. In CSIC, 74% of normal-test records duplicate normal-train content and every PUT request is anomalous. SR-BH has an estimated 5–14% of rows mislabeled. open-appsec's attacks are two-header `GET /?p=` requests that header shape alone separates from its benign set. Published CSIC F1 scores of 96–99.9% come from random splits, so the project's group-aware 70% F1 and 29% false-alarm rate is closer to an honest number. The one quantified cross-application test found shows a Random Forest's detection rate falling from 1.00 to 0.22. Sources can be combined safely only if five conditions hold. Each training source must supply both classes from one context. Host, IP, response and session fields must be stripped. Deduplication and grouping must happen before any split. Class ratios must be equal across sources. Success must be judged on leave-one-dataset-out results rather than pooled accuracy. The earlier candidate list (`docs/aday-veri-setleri.md`) also needs seven corrections. For example, SR-BH has no `full_http_request` column and is CC0-licensed, and modsec-learn's benign side is query strings only.

## Five sources hold full labeled requests; the rest hold fragments

`scripts/extract_features.py` computes 16 base and 5 pattern features from the method, path, query and form body. It stores headers but does not scan their contents in v1, and it cannot parse JSON or multipart bodies (`docs/oznitelik-cikarici.md`). A dataset therefore qualifies only if each record is one HTTP request with those fields and its own label. Few public datasets meet that bar. **Only five sources carry a real method, path, query, headers and body per request: CSIC 2010, ECML/PKDD 2007, SR-BH 2020, the open-appsec WCP legitimate set and ATRDF** ([msudol mirror](https://github.com/msudol/Web-Application-Attack-Datasets); [LIRMM](https://www.lirmm.fr/pkdd2007-challenge/); [Dataverse](https://doi.org/10.7910/DVN/OGOIXX); [WCP README](https://github.com/openappsec/waf-comparison-project); [ATRDF](https://github.com/ArielCyber/Cisco_Ariel_Uni_API_security_challenge)).

Three other sets fill part of that schema. **ModSec-WP** (2026) keeps the request line, Host, User-Agent and body ([Zenodo 21872151](https://zenodo.org/records/21872151)). The **30-day ModSecurity production logs** keep full headers but contain only attacks ([Zenodo 17178461](https://zenodo.org/records/17178461)). **Biblio-US17** offers 47 million real requests, but only method and URI ([README](https://dtstc.ugr.es/neus-cslab/wp-content/uploads/2023/08/README.txt)). Everything else listed as an "HTTP attack dataset" is either a fragment or a flow table. Fragments hold query strings (modsec-learn, Fwaf), parameter values (HttpParams) or bare payloads. Flow tables hold no request content; WEB-IDS23 states that "unencrypted payloads were not recorded" ([arXiv 2502.03909](https://arxiv.org/html/2502.03909v1)).

The two classic datasets now survive only as third-party copies. On 17 October 2026 the official CSIC host refused connections on port 443 and timed out on port 80, and the TORPEDA/CSIC 2012 files on the same host went down with it ([CSIC page](https://www.tic.itefi.csic.es/dataset/)). The LIRMM ECML/PKDD "Data" link returned **HTTP 500** ([LIRMM data link](http://www.lirmm.fr/pkdd2007-challenge/Donnees/index.html)). The msudol GitHub mirror is a clone of the Uruguayan GSI GitLab, which still responds. It holds the three original CSIC text files and the original ECML XML zip, and `data/http-mini/` was built from it. Avoid derived copies as primary sources. The Hugging Face `bridge4` CSIC split totals 61,792 rows, which matches neither the 61,065 papers usually quote nor the 97,065 raw total ([HF bridge4](https://huggingface.co/datasets/bridge4/CSIC2010_dataset_classification)). Some papers use a "CSIC2010 v2" of **223,585 rows** that has no primary documentation. Its 18 tabular variables and per-session payload re-joining point to a parameter-level expansion of the same capture ([arXiv 2412.16791](https://arxiv.org/abs/2412.16791)). No verified copy can be downloaded, so it should stay out of the project.

Licensing splits the field sharply. **SR-BH 2020 is CC0, open-appsec's benign set is Apache-2.0, ModSec-WP and the 30-day logs are CC-BY-4.0, and HttpParams is MIT** ([Dataverse](https://doi.org/10.7910/DVN/OGOIXX); [WCP README](https://github.com/openappsec/waf-comparison-project); [Zenodo 21872151](https://zenodo.org/records/21872151); [Zenodo 17178461](https://zenodo.org/records/17178461); [HttpParams](https://github.com/Morzeux/HttpParamsDataset)). **CSIC 2010 and ECML/PKDD 2007 have no license at any reachable primary source.** Mirrors variously label CSIC as GPL-3.0, MIT or "© Original Authors" ([Kaggle search](https://www.kaggle.com/api/v1/datasets/list?search=csic)). The CSIC authors themselves noted that ECML downloads were restricted behind a username and password ([TORPEDA paper](https://recsi2012.mondragon.edu/es/programa/recsi2012_submission_73.pdf)). ATRDF and modsec-learn ship with no license file at all. The open-appsec attack set is described as "mostly under MIT", but its source payload repository carries GPL-3.0 ([mgm-web-attack-payloads](https://github.com/openappsec/mgm-web-attack-payloads)). In practice, the 1,000 CSIC requests already committed in `data/http-mini/` rest on unverified terms. Any future committed sample should come from the CC0, Apache-2.0 or CC-BY sources, with attribution where CC-BY requires it.

The 2019–2026 releases mostly widen attack coverage; they add little clean benign traffic. Log4Shell shows up in **220 open-appsec attack requests** ([malicious.zip](https://downloads.openappsec.io/waf-comparison-project/malicious.zip)), in an ATRDF LOG4J class, and in 488 `jndi` lines in the 30-day logs. ATRDF is the main research source of labeled JSON API traffic, with log-forging and cookie-injection classes ([ATRDF](https://github.com/ArielCyber/Cisco_Ariel_Uni_API_security_challenge)). No labeled dataset with deserialization payloads turned up. The largest synthetic set, FADE, holds 50 million requests but sits behind an IEEE DataPort subscription ([FADE](https://ieee-dataport.org/documents/firewall-attack-detections-and-extractions-fade)). The PCAP route yields very little. After Engelen et al. cleaned CIC-IDS2017's web-attack traffic, only **151 brute-force, 27 XSS and 12 SQLi flows** still carried payload ([Engelen et al. 2021](https://lirias.kuleuven.be/retrieve/713070)). The CIC download server also returned "Server error" on the check date ([cicresearch.ca](http://cicresearch.ca/CICDataset/CIC-IDS-2017/)).

## Every candidate carries a flaw that inflates or caps scores

### CSIC 2010 has heavy duplication, a method shortcut and a broad "anomalous" label

CSIC 2010 is mostly copies. Counted by request line plus body, **the 36,000-record normal training file has only 9,644 distinct requests**, the normal test file 9,622, and the 25,065-record anomalous file 15,964. Just 626 shared keys account for **26,704 of the 36,000 normal-test records (74%)** that also appear in normal-train ([mirror files](https://github.com/msudol/Web-Application-Attack-Datasets/tree/master/OriginalDataSets/csic_2010)). A random split of the full corpus therefore measures memorization. The project's content grouping (`docs/http-veri-ayrimi.md`) is the right defense, and it matters more at full scale than it did on 1,000 requests.

The full corpus also carries shortcuts the balanced sample hid. **All 397 PUT requests are in the anomalous file.** The normal-test file is 78% GET (28,000 of 36,000), against 60% GET in the anomalous file (15,088 of 25,065). The project's sample was deliberately balanced at 250 GET and 250 POST per class, so the current models have never seen this method signal. HTTP2vec's authors also found that "each anomalous request ended with a '\n' character and not '\r\n'" ([Gniewkowski et al. 2021](https://arxiv.org/abs/2108.01763)). The two raw mirrors differ by about 492 KB per normal file. That points to different line endings in different copies (not confirmed by a diff), so whether the artifact is present depends on which copy is downloaded. Header values barely vary: CSIC shows "a narrow range of unique values" ([Sivri et al. 2022](https://annals-csis.org/Volume_32/drp/pdf/147.pdf)), the Host is always the same, and all traffic comes from "a single domain from a single computer" ([arXiv 2002.04059](https://arxiv.org/pdf/2002.04059)).

The deepest problem is what the label means. The dataset's maintainers write that "we do not know how real attacks and anomalous traffic distribute in this dataset". Some anomalous requests are simply valid requests "modified with typos errors in parameters" ([OriginalDataSets README](https://github.com/msudol/Web-Application-Attack-Datasets/blob/master/OriginalDataSets/README.md)). Aharon et al. found that "most of the anomalous requests which overlap with normal requests actually have no malicious payload", such as an invalid Spanish national ID. They also found that **8 of 38 endpoints have no normal representation** ([Aharon et al. 2024](https://arxiv.org/abs/2405.11247)).

### ECML/PKDD 2007's values are random strings and its attacks look generated

ECML/PKDD began as real traffic, but every URL, parameter name and value was replaced "with randomly generated strings" ([OriginalDataSets README](https://github.com/msudol/Web-Application-Attack-Datasets/blob/master/OriginalDataSets/README.md)). As a result, "no URI, parameter name or value appears twice", which made the dataset "useless for carrying on n-gram analysis" ([Betarte et al. 2018](https://arxiv.org/abs/1803.05529)). Headers are randomized and exotic, for example `UA-CPU: MIPS` and `Via: HTTP/5.7`, so header-derived features learned on ECML will not transfer. **The seven attack classes are nearly uniform, at 1,825–2,302 each** ([ecml split](https://github.com/msudol/Web-Application-Attack-Datasets/tree/master/OriginalDataSets/ecml_pkdd/dataset_ecml_pkdd_train_test)). That points to deliberately generated attack sets rather than a natural mix. About 10% of attacks are "out of context", such as LDAP injection against a server with no LDAP ([LIRMM](https://www.lirmm.fr/pkdd2007-challenge/)). The GSI re-split also puts every attack in the test file, so supervised use requires a fresh split.

### SR-BH 2020 is real traffic, but its labels are noisy and some columns leak

SR-BH is the most realistic large source. It covers 12 days of Internet traffic to one WordPress VM, labeled from ModSecurity CRS 3.3.0 alerts and then reviewed ([Dataverse](https://doi.org/10.7910/DVN/OGOIXX)). Its labels are noisy, and two audits disagree on how noisy. X-WAD found "approximately 13.8% of the dataset is mislabeled" and published **126,003 row indexes** to flip from normal to anomalous. It also warns that some benign rows "may have been incorrectly relabeled" ([X-WAD](https://arxiv.org/abs/2608.27172)). WAMM's LLM pass flagged a smaller set of **48,522** benign rows, about 5.3% of all rows or 9.2% of benign ([WAMM](https://arxiv.org/abs/2512.23610)). WAMM also showed that some SR-BH classes cannot be detected from the request alone. The smuggling samples lack Content-Length and Transfer-Encoding headers, the dictionary password attacks are "indistinguishable from normal login HTTP requests", and the verb-tampering labels relied on response content.

Label noise visibly caps scores: fixing the labels raised ModernBERT F1 from **86.16% to 98.29%** ([X-WAD](https://arxiv.org/abs/2608.27172)). The benign class is also highly redundant, though by how much is disputed. WAMM's LSH removed about 519K redundant benign payloads, while WADBERT's deduplication kept 161,334 benign rows ([WADBERT](https://arxiv.org/abs/2601.21893)). The CSV also contains columns that leak the label: Docker-internal IPs (172.26.0.x), ports, timestamps and `response_*` fields ([CSV](https://dataverse.harvard.edu/api/access/datafile/6319496)).

### open-appsec's benign and attack sets differ in header shape alone

open-appsec's benign set is the best modern benign traffic available. It was recorded while browsing real sites and doing sign-ups, searches and cart actions, "ensuring the presence of 100% legitimate requests" ([blog 2023](https://www.openappsec.io/post/best-waf-solutions-in-2023-real-world-comparison)). Its attack set is a different kind of object. Each attack is a `GET /?p=<payload>` with only a `User-Agent` (Firefox/105) and a `Connection` header, while benign records carry 10–20 real Chrome headers on real hostnames ([legitimate.zip](https://downloads.openappsec.io/waf-comparison-project/legitimate.zip); [malicious.zip](https://downloads.openappsec.io/waf-comparison-project/malicious.zip)). Any classifier trained on that pair learns to count headers. The attacks are also lopsided: **XSS and path traversal make up 95% of the 73,924, and SQLi only 916**. The documentation is inconsistent too. The README says 185 sites in 12 categories, the 2026 blog says 692 websites in 14 categories ([blog 2026](https://openappsec.io/post/best-waf-solutions-in-2026-real-world-comparison)), and some sites appear as two files.

### Newer releases and most online uploads add new flaws

The newer releases add their own problems. ModSec-WP's authors warn that "a substantial fraction of rows are near-identical", and only 12,597 rows are normal ([Zenodo 21872151](https://zenodo.org/records/21872151)). In the 30-day logs, the most frequent rules are protocol-enforcement and restricted-file rules (920xxx, 930130), not injection rules. "Anomalous" there means whatever CRS flags, scanner noise included ([Zenodo 17178461](https://zenodo.org/records/17178461)). ATRDF targets a local `127.0.0.1:5000` API, so its traffic is synthetic.

Most Hugging Face and Kaggle uploads are worse. In a 199,793-request Kaggle set, "the label of the targeted resource, encoded in the HTTP request path field, determines the message class" ([Research Square](https://www.researchsquare.com/article/rs-10802265/v1)). `vyykaaa/dataset-web-attack` pairs Juice Shop normals with DVWA attacks ([HF](https://huggingface.co/datasets/vyykaaa/dataset-web-attack)). The 2.4M-row `puyang2025/waf_data_v2` mixes SR-BH-style rows with `normal`-labeled requests that contain `sleep(15)` ([HF](https://huggingface.co/datasets/puyang2025/waf_data_v2)). Two sets are contaminated with CSIC itself. HttpParams takes its benign values from CSIC 2010 ([HttpParams](https://github.com/Morzeux/HttpParamsDataset)), and SecureAI-SE builds its attacks inside CSIC normal-request envelopes ([HF SecureAI-SE](https://huggingface.co/datasets/SecureAI-SE/http-attack-requests)). Combining either with CSIC leaks content across datasets.

## Group-aware 70% F1 sits near CSIC's honest ceiling

CSIC is still unavoidable for comparison. A review of 63 deep-learning web-attack studies (2010 to September 2021) found that **29 used CSIC 2010, 3 used ECML/PKDD and 37 used private data** ([Alaoui & Nfaoui 2022](https://doi.org/10.3390/fi14040118)). The headline CSIC numbers rest on weak protocols. WADBERT reports F1 99.63% on a 70/30 split with no grouping ([WADBERT](https://arxiv.org/abs/2601.21893)). HTTP2vec reports 96.9% under 5-fold cross-validation ([Gniewkowski et al. 2021](https://arxiv.org/abs/2108.01763)). Sivri et al. reached F1 ≈0.99 after splitting header-swapped copies of normal requests at random, which puts near-duplicates on both sides of the split ([Sivri et al. 2022](https://annals-csis.org/Volume_32/drp/pdf/147.pdf)).

Models trained only on normal data, CSIC's original protocol, report clearly lower numbers. Isolation Forest, for example, reaches F1 84.12% ([Babaey & Faragardi 2025](https://arxiv.org/abs/2504.14122)). No paper in the literature reviewed reports CSIC results under endpoint-, template- or near-duplicate-disjoint splits. An audit of 30 top-venue security-ML papers found sampling bias and data snooping at least partly present in 90% and 73% of them ([Arp et al. 2022](https://arxiv.org/abs/2010.09470)). The project's numbers should therefore be compared with the roughly 82–89% F1 of normal-only models, not with random-split 99% figures.

Four factors explain most of the plateau. The largest is **label semantics**. Some CSIC "anomalous" requests are well-formed values that only break a per-parameter format rule, which aggregate length, count and character-class features cannot see. Second, **near-constant headers** carry almost no class signal. Third, **grouping removes the template memorization** that inflates random-split results. Last, the models learn from **only 604 training requests**, and a ROC AUC of 0.765 shows that ranking quality, not just the 0.5 threshold, limits the score (`README.md`).

The full corpus tests the last factor directly. A learning curve under the same grouping will show whether features or sample size are the binding limit. Hand-built tabular features are not a dead end. On SR-BH, XGBoost on TF-IDF plus length, keyword and entropy features beat DistilBERT (macro-F1 **96.77% vs 85.47%**; [WAMM](https://arxiv.org/abs/2512.23610)), as long as the features see parameter values.

Expect a sharp drop when the model meets another dataset. Riverol et al.'s Random Forest reached **TPR 1.00 and FPR 0.00002 in training, but TPR 0.22 and FPR 0.0161 on the application it was meant to protect** ([Riverol et al. 2024](https://arxiv.org/abs/2407.18445)). The same study measured ModSecurity CRS at 39.69% FPR on real Drupal traffic. A search snippet of earlier work by the same group reports that a classifier "designed for one dataset cannot be used in other ones" when moving from ECML/PKDD to Drupal ([Betarte et al., ICMLA 2018](https://www.researchgate.net/publication/329514915_Web_Application_Attacks_Detection_Using_Machine_Learning_Techniques)).

At real attack rates, the false-alarm rate matters more than F1. Biblio-US17's real traffic contains attacks at about 0.77% (327,906 against 42,473,128 clean; [README](https://dtstc.ugr.es/neus-cslab/wp-content/uploads/2023/08/README.txt)). At that rate, the current 69.7% recall and 29% false-alarm rate give a precision of about 1.8%, or roughly 54 false alarms per true detection (computed here). This is the base-rate trap Arp et al. warn about.

## Scale up in three tiers, starting with data already in reach

### Full CSIC and SR-BH form the first tier

**Full CSIC 2010 comes first.** It is cheap: the project already parses the format, and the grouping and split code applies unchanged. It also answers the most urgent question, whether the 70% is limited by data size, while staying comparable with the literature. Convert from the raw msudol text files, not from CSV, Hugging Face or "v2" copies. Keep the Latin-1 bytes, normalize line endings before anything reads the raw text, and reduce the absolute `http://localhost:8080/...` target to path and query. Because of the PUT and GET-share artifacts, report results with and without the method feature. The near-content rule compares pairs within each path-plus-parameter-name block. That is still feasible at 97k requests. At SR-BH scale it will likely need a MinHash/LSH pre-filter like WAMM's (an inference, not measured).

Respect the project's own rules while scaling. Four models have already seen the old 199-request test set (`README.md`). Assign every content group that touches the old 1,000 requests to training, the same way the four inspected examples were pinned to training (`docs/http-veri-ayrimi.md`), and freeze a fresh test split once. Changing `extract_features.py` stops the recorded experiments' test scripts. New converters and extractor upgrades therefore go in new scripts under a new experiment version. Raw data goes under `data/raw/`, outputs under new `data/processed/` folders.

**SR-BH 2020 comes second and becomes the main scale-up set.** It is real traffic, both classes come from the same site (so source leakage between classes is impossible), it is CC0, and 2024–2026 work uses it widely. Download `data_capec_multilabel.csv` from Dataverse and verify its md5, `173ec515308bdce5aec19cfd5b792596` ([Dataverse](https://doi.org/10.7910/DVN/OGOIXX)). Map the columns as follows:

| Target field | Source in the SR-BH CSV |
|---|---|
| method | `request_http_method` |
| path and query | split from `request_http_request` |
| headers | the 11 header columns, skipping empty cells |
| body | `request_body` |
| label | 1 − `000 - Normal`; keep the CAPEC vector as metadata |

Drop every network and response column. Run each experiment twice: on the original labels, and with X-WAD's 126,003 flips applied by `original_index` ([mislabeled_indexes.csv](https://github.com/mattebit/x-wad/blob/main/experiments/srbh2020/mislabeled_indexes.csv)). Neither label set is ground truth. Consider dropping the CAPEC classes WAMM showed cannot be identified from the request alone. Check the CSV quoting of multi-line bodies before trusting the parse.

### open-appsec benign and ECML/PKDD test transfer and widen attack coverage

**Use open-appsec's legitimate set as a benign-only false-alarm test, never paired with its own attack set for training.** Its 692 per-site files give a natural group ID for grouped evaluation. Many of its bodies are JSON, which the current extractor turns into `null` features. Either add JSON body support in a new extractor version, or evaluate on non-JSON requests only, so missing values do not become a source signal.

**Use ECML/PKDD 2007 for its LDAP, XPath and OS-command injection attacks**, which are absent from CSIC 2010 ([TORPEDA paper](https://recsi2012.mondragon.edu/es/programa/recsi2012_submission_73.pdf)). Train within ECML with grouped splits, or use it only as a cross-dataset test. Decide up front whether out-of-context attacks count as anomalous, and treat header and value-vocabulary features as unusable there.

| Set | Question it answers | Constraint |
|---|---|---|
| ModSec-WP | Does a model hold up on a second WordPress testbed that has both classes? | Deduplicate first; small normal class |
| ATRDF | Does it detect JSON API attacks such as Log4j and log forging? | Needs JSON support; no license, so local use only |
| 30-day ModSecurity logs (already in `data/raw/owasp/`) | What is its recall on real production attacks? | Attacks only, CRS-defined labels |
| Biblio-US17 | Do path and query features alone hold up on real traffic? | Headers and body always empty; NC-ND limits redistribution |

### Fragment and mashup sources stay out of training

Keep five groups of sources out of training. modsec-learn holds only query strings, covers SQLi only, and takes its benign and attack sides from different sources; at most it is a cross-test. Fwaf and HttpParams hold fragments, and HttpParams carries CSIC content. Undocumented Hugging Face and Kaggle mashups are leaky or contaminated. CIC PCAPs need heavy reassembly and per-request relabeling for a few hundred attack requests. WEB-IDS23 has no request content at all.

### Most conversions take one script; three need schema work

| Dataset | Mapping to `requests.jsonl` | Effort | Watch for |
|---|---|---|---|
| CSIC 2010 | Split on the request-line regex; `urlsplit` the absolute URL; header list; body after the blank line; label from file name | Low | Latin-1 bytes, LF/CRLF artifact, duplicates across the two normal files |
| SR-BH 2020 | Column mapping above; binary label from the Normal column; CAPEC vector and X-WAD flag as metadata | Low–medium | Quoting in the 436 MB CSV; leaky network and response columns |
| open-appsec benign | Rename `{method,url,headers,data}`; split `url`; site group ID from file name | Low | JSON bodies; 7.3 GB unpacked; CDN requests |
| ECML/PKDD 2007 | Parse the original XML; label = `type != Valid`; keep `inContext` and `attackIntervall` | Low–medium | Random headers; needs a fresh split |
| ATRDF | Extract 7z; map `request.{method,url,headers,body,Attack_Tag}`; drop the response | Medium | Schema verified for dataset 1 only |
| ModSec-WP | Read the `.xlsx`; split `request_line`; Host and User-Agent are the only headers | Medium | Near-duplicates; small normal class |
| 30-day ModSecurity | Parse audit sections B (headers) and C (body) | Medium | No benign class; CRS-defined labels |
| Biblio-US17 | Method and URI only | Low | Header and body features always empty |

## Merge sources only where both classes share one context

The most damaging mistake would be benign traffic from one source paired with attacks from another. That is the setup in which Riverol et al. saw TPR collapse from 1.00 to 0.22 ([Riverol et al. 2024](https://arxiv.org/abs/2407.18445)): the model learns which dataset a request came from instead of which requests are attacks. It is exactly the project's own *kaynak sızıntısı* (source leakage) rule. Flow-IDS work reached the same conclusion. It recommends a common schema built "from the intersection of the features" across datasets, and dropping any IP-related field that cannot be standardized without artifacts ([Apruzzese et al., XeNIDS](https://arxiv.org/abs/2203.04686)). HTTP-specific work adds three fixes: randomize Host values, strip source-specific URI prefixes, and remove headers that appear only in attacks ([Gniewkowski et al. 2021](https://arxiv.org/abs/2108.01763)). The table maps each leak channel found in the candidate datasets to its fix.

| Leak channel | Where it appears | Mitigation |
|---|---|---|
| Host and absolute URL | CSIC `localhost:8080`, SR-BH `test-site.com`, ATRDF `127.0.0.1:5000`, open-appsec real hostnames | Reduce to path and query; never use Host as a feature |
| Network, time and session fields | SR-BH IPs, ports and timestamps; cookies and session IDs everywhere | Drop during conversion |
| Response fields | SR-BH `response_*`, ModSec-WP status and body | Drop them; the design is request-only |
| Header shape | open-appsec attacks (2 headers) vs benign (10–20); ECML random headers; CSIC constant headers | Use a common header subset, or no header features in cross-source runs |
| Line endings and encoding | CSIC anomalous LF; Latin-1 vs UTF-8 across sources | Normalize CRLF; record and apply the encoding per source |
| Method | CSIC PUT only in anomalous; GET share 78% vs 60% | Stratify by class × method (already done); ablate method |
| Endpoint identity | Kaggle 199,793 set; Juice Shop vs DVWA uploads; CIC's DVWA host | Reject mixed-app sets; group by endpoint for transfer tests |
| Missing fields | Biblio-US17 has no headers or body; JSON bodies parse to `null` | Handle missing values the same way everywhere; evaluate URI-only sources on URI features only |
| Cross-dataset copies | HttpParams and SecureAI-SE built on CSIC; `puyang2025` holds SR-BH-like rows | Hash every source and remove cross-source overlaps before splitting |
| Duplicates | CSIC's 74% overlap; SR-BH benign redundancy; ModSec-WP near-identical rows | Exact plus near-duplicate grouping before any split |

**Deduplicate before splitting, inside and across sources.** Run exact grouping, then near-duplicate grouping, then group-aware stratified splits within each source. That is the current pipeline, applied per source, and WAMM's MinHash/LSH step is its scalable version ([WAMM](https://arxiv.org/abs/2512.23610)). Fit all preprocessing on training data only. Fitting on the whole dataset before splitting counts as data snooping ([Arp et al. 2022](https://arxiv.org/abs/2010.09470)).

**Equalize class ratios per source when pooling.** Class balance differs by source. Distinct CSIC requests are roughly 45% normal and 55% anomalous. SR-BH is 58/42 on its original labels and about 44/56 after the X-WAD fix (computed). In a pooled model, source identity would then predict the label even if every source were clean. A source-predictability probe will almost certainly show that the 21 features identify each source, because the applications differ. That is acceptable only if every source enters training with the same class ratio, so knowing the source says nothing about the label.

**Map every label to one binary scheme and record what "anomalous" meant in each source.** In CSIC it means a deviation from one application's normal profile, typos included. In ECML/PKDD it means an attack, possibly out of context. In SR-BH it is a CAPEC category assigned from WAF alerts plus review. In the 30-day logs it is a CRS rule match. Ring et al. warn that IDS-derived labels "might be wrong since an IDS might be imperfect" ([Ring et al. 2019](https://arxiv.org/abs/1903.02460)). Store the source label as metadata, and report per-source results alongside pooled ones.

**Evaluate in three layers.** The first layer is within-source grouped results. The second is a train-on-A, test-on-B matrix across CSIC, SR-BH, ECML/PKDD and ModSec-WP. In that matrix, open-appsec benign serves as a false-positive-only column and the 30-day logs as a recall-only column. The third layer is leave-one-dataset-out results for any pooled model. The literature reviewed has no grouped-split matrix like this for HTTP requests, so building one is itself a contribution. Every row should report the confusion matrix, the false-alarm rate, PR-AUC and ROC-AUC, the dataset version and the deduplication rule used. It should also report TPR at 1% FPR, which Scano et al. call "a reasonable value commonly adopted in the literature" ([Scano et al.](https://arxiv.org/abs/2406.13547)).

**Add attack diversity only by injecting payloads into the same benign envelopes.** Putting payloads inside real benign requests means both classes share headers, hosts and encoding. SecureAI-SE does this with CSIC envelopes and randomized Hosts ([HF SecureAI-SE](https://huggingface.co/datasets/SecureAI-SE/http-attack-requests)). The Hybrid 2020 dataset converted valid CSIC and ECML requests using PayloadsAllTheThings ([JCSANDM](https://journals.riverpublishers.com/index.php/JCSANDM/article/download/2263/5081/21237)). For this project, the natural version is open-appsec or GoTestWAF payloads ([GoTestWAF](https://github.com/wallarm/gotestwaf)) placed into open-appsec legitimate requests. It should include a control set in which parameters are swapped for other benign values, so the model cannot simply learn "this request was modified". The control is a recommendation from this analysis, not a published method.

## Limitations: payload corpora and self-generated data remain open

**Payload corpora and self-generated datasets were not fully researched.** The note covering OWASP CRS regression tests, SecLists, PayloadsAllTheThings and in-house generation (testbeds, honeypots) was cut off mid-write, and only its short summary survives. That summary reports that SecLists and PayloadsAllTheThings are the largest permissively licensed corpora, that most Kaggle SQLi/XSS sets carry "Unknown" licenses, and that their benign sides largely derive from CSIC. This report did not verify any of it. Before the injection strategy above is implemented, a separate pass should verify corpus sizes, licenses, label quality and CSIC overlap. It should also design the in-house generation option, including the privacy and KVKK constraints already noted in `docs/aday-veri-setleri.md`. Honeypot data was surveyed only briefly. The two research honeypot corpora found (754,281 and about 1.24 million requests) had no confirmed public release ([PMC12197152](https://pmc.ncbi.nlm.nih.gov/articles/PMC12197152/); [ResearchGate](https://www.researchgate.net/publication/395574853_Intercepting_and_Monitoring_Potentially_Malicious_Payloads_with_Web_Honeypots)).

**Several figures rest on metadata and partial reads, not full downloads.** All checks ran on 17 October 2026 using HEAD and range requests, and no large archive was downloaded. As a result, several things remain unmeasured. Near-duplicate rates were measured only for CSIC, and that exact count ignored headers. SR-BH's CSV quoting was not checked. Neither was open-appsec's claim of a purely benign set, or its share of CDN traffic. ATRDF datasets 2–4 and the contents of the Biblio-US17 tarball were not inspected.

**Sources conflict on four points.** The SR-BH mislabel rate is 5.3% (WAMM) or 13.8% (X-WAD). SR-BH's benign redundancy is either 161,334 rows kept or about 519K removed. open-appsec's site count is 185 or 692. For Biblio-US17 access, idUS's API reports open access, but a search summary describes a request form ([idUS](https://idus.us.es/handle/11441/148254)). The CSIC outage may be temporary; the Wayback Machine was offline, so archived pages could not be checked. CSIC and ECML license terms remain unknown. No published study measures how much random splits inflate CSIC scores, or how predictable an HTTP request's source dataset is.

## Conclusion

The binding constraint is not data volume. It is how many requests are distinct, correctly labeled and drawn from a single context. CSIC's 97,065 requests shrink to about 35,000; SR-BH's benign half shrinks by an amount two deduplication studies cannot agree on; and open-appsec's million benign requests have no attacks recorded in the same context. Size figures should be read only after deduplication and grouping. The project's grouping policy, so far treated as a precaution for a 1,000-request exercise, is the part of the pipeline that decides whether bigger datasets yield honest numbers.

The next result worth chasing is transfer, not a higher CSIC F1. A modest score that holds across CSIC, SR-BH, ECML/PKDD and ModSec-WP, together with a false-alarm rate measured on open-appsec's real-site traffic, would say more than any within-CSIC gain. The literature has no grouped cross-dataset table for HTTP requests. Producing one with the existing Random Forest and logistic regression pipeline would be a real finding even if the scores drop. It would also show which of the 21 features capture attacks and which only capture the application they were measured on.
